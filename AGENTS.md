## ⚠️ ПЕРЕД КАКОЙ ЛИБО РАБОТОЙ

**Всегда начинай с пулла актуальной версии репозитория** (правило заказчика,
2026-10-21):

```
git pull origin main
```

Заказчик может править задачи/документы с другой машины — без пулла легко
перетереть его правки. Дальше работай только на актуальном состоянии.
После задачи — коммит и `git push origin main`.

**Каждый аспект/этап — в новом чате** (постоянное правило заказчика,
2026-10-21): реализация каждого следующего аспекта или этапа начинается
в НОВОМ чате; текущий чат закрывается после приёмки заказчиком.

### Как заказчику начать новый чат (шаблон первой фразы)

Достаточно ОДНОЙ строки — агент дальше всё найдёт сам (этот файл,
PLAN.md, дизайн-доки, последний коммит приёмки):

```
git pull, работаем по ЭТАП-2, аспект N «Название»
```

Варианты первой фразы:
- Следующий аспект известен (номер и название записаны в коммите
  приёмки предыдущего и в PLAN.md):
  `git pull, работаем по ЭТАП-2, аспект 6 «Новые зоны и кварталы»`
- Номер не помните: `git pull и следующий аспект по PLAN.md`
  — агент сам читает PLAN.md → ЭТАП-2-город.md → дизайн-док аспекта.
- Новый этап: `git pull, работаем по этапу 3 — прочитай TZ.md и PLAN.md`.
- Правки по итогам игры: `git pull, правки приёмки: <что не понравилось>`.

Дальше агент сам: pull → чтение AGENTS.md и дизайн-доков → вопросы
заказчику (если решения не зафиксированы) → реализация → тесты ×3 →
живой прогон сцены → версия + CHANGELOG + PLAN + exe → коммит и push.
Заказчик играет; «принимаю» — приёмка фиксируется документами и
коммитом, чат закрывается; правки — тем же чатом, пока не примет.

**Обязанность агента при фиксации приёмки** (каждый раз, когда задача
принята): в коммите приёмки и в PLAN.md указать следующий шаг —
«Следующий аспект: N «Название» — начинать в новом чате», чтобы
следующему чату было что найти по первой фразе.

## Что это за проект

**«Пепел и Мана»** — компьютерная игра (Godot 4.7, GDScript, Windows 64):
градострой + выживание + магия + рогалик в одном мрачном пауэр-фентези мире.
Игрок — герой-основатель: ставит город, управляет жителями, лично ходит
в данжи и путешествует по карте мира. Референсы заказчика: RimWorld (мир
живёт программно, время пути по дням) + классический рогалик-данж.

Заказчик: **SDVGames-Studio** (vrazhin). Репозиторий:
`https://github.com/SDVGames-Studio/pepel-i-mana`. Общение и документация —
на русском; всё, что заказчик решил, зафиксировано в `QUESTIONS.md`
(ответы №1–105) и заголовках этапов в `PLAN.md`.

### Текущее состояние (обновляй при коммите)

- Этап **M14 закрыт целиком** (12 частей A–L, см. `CHANGELOG_M14.md`).
- Версия: смотри `data/version.json` (источник правды), сборка `build/ПепелИМана.exe`.
- Тесты: `tests/run_all.gd`, **все зелёные**, число проверок — в последней
  секции changelog. Проверенные, но отложенные вещи — в конце `PLAN.md`.

## Как устроен код

### Архитектура

- **Godot 4.7**, язык GDScript, рендер Forward+, вьюпорт 1920×1080,
  растяжение `canvas_items`.
- **Автозагрузки** (project.godot): `Game` (`scripts/game.gd`) — глобальное
  состояние (город, мир, герой, инвентарь, флаги переходов); `Loc`
  (`scripts/loc.gd`) — переводы (`Loc.t("ключ")`).
- **Сцена = локация**: `scenes/city.tscn` (город), `world.tscn` (карта мира),
  `dungeon.tscn` (данж), `trade_camp.tscn` (лагерь торговцев),
  `main_menu.tscn`. Переходы — `get_tree().change_scene_to_file`, контекст
  передаётся полями `Game` (см. «контекст локации» в game.gd).
- **Паттерн каждой локации**: `<loc>.gd` — ввод/жизнь сцены;
  `<loc>_sim.gd` — ЧИСТАЯ логика без рендера (city_sim — RefCounted, живёт
  в Game и тикает, пока сцена другая); `<loc>_view.gd` — рисование на
  `_draw()`; `<loc>_hud.gd` — панели/тосты/подсказки; `<loc>_map.gd` —
  сетка тайлов и пути (AStar2D).

### Данные отдельно от кода (важно!)

Вся математика и баланс — в `data/*.json`: `city.json` (город, hero_work,
автономия, план самостроя), `residents.json` (черты, беженцы, болезни,
отношения), `balance.json`, `dungeon.json`, `world.json`, `weather.json`,
`skills.json`, `items.json`, `weapons.json`, `quests.json`, `story.json`,
`laws.json`, `religion.json`, `factions.json`, `giants.json`, `fauna.json`,
`version.json` (версия игры). Все строки интерфейса — `loc/ru.json`.
**Правь баланс конфигом, а не кодом** — так заведено.

### Сейв

`scripts/save_game.gd` — человекочитаемый JSON в `user://saves/save.json`.
Сохраняется всё (город/мир/герой/квесты/сюжет/погода). Векторные поля
кодируются тегами (`v2`/`v2i`/`pv2`/`d`). Данж транзитен (не сохраняется).
Новые поля симуляций ДОБАВЛЯЙ и в save, и в load.

## Игровой цикл и механики (краткая карта)

1. **Соло-старт**: новая игра = герой + один житель-основатель (староста).
   Поселенцы приходят сами (беженцы: шанс в день, ранний бонус, пока <8
   жителей; нужен дом и запас еды). С 10 жителей город можно объявить
   **автономным** (кнопка «Автономия»): самострой без старосты, план
   расширяется, беженцы ×1.5, настроение +5.
2. **Город**: свободные зоны и здания по категориям; жители с профессиями,
   чертами, настроением, парами, детьми, болезнями; производство даёт кучи
   у зданий, **носильщик** сносит их на склад в общий пул; дороги ускоряют;
   ежедневный **самострой** по `autobuild_plan` (город строит сам), затем
   кольцо стен с воротами и вышками.
3. **Угрозы**: нарастающие волны мутантов из аномалии, осады бандитов
   (гнёзда растут уровнями), магические бури, лес (гнев за вырубку → духи →
   Древень; посадка леса успокаивает), некромант на кладбище (тайная армия),
   вампиры/личи/дракон/гиганты в мире.
4. **Герой**: одним персонажем; в городе — **ручной труд по E** (рубить
   дерево 5 ударов, добывать скалу 4, достраивать площадку; при соло-старте
   строителей нет — это работа героя); в данже — бой (5 типов оружия,
   экипировка, заклинания из рун, зелья/свитки), лут в общий пул;
   анти-кайт у монстров.
5. **Мир**: карта мира с тайлами и биомами; POI (данжи, руины, лагеря,
   поселения, обелиски, торговцы); путь по дням, мир и город живут в пути;
   туман войны, следы, лодка/лошадь, фракции и репутация.
6. **Обвязка**: сейв/автосейв, квесты (доска Q), кодекс и статистика (K),
   законы (L), вера (храм, божества), погода и сезоны, летопись (C),
   сюжетная рамка «Пепел vs Мана» (6 глав, выбор стороны, песочница
   продолжается).

## Как работать над задачей (процедура)

1. `git pull origin main`.
2. Контекст: `TZ.md` (что за игра), `QUESTIONS.md` (решения заказчика),
   `PLAN.md` (план и список правок), последний `CHANGELOG_M*.md` (как
   устроено сейчас). Задача про конкретную игровую систему — сначала прочитай
   её дизайн-док в `docs/design/<модуль>.md` (правила работы с ними —
   в `docs/design/README.md`).
3. Правка: баланс → конфиг в `data/`; логика → `*_sim.gd`; показ →
   `*_view.gd`/`*_hud.gd`; строки → `loc/ru.json` (ключи без хардкода).
4. **Тесты**: `test.bat` или
   `"F:\steam\steamapps\common\Godot Engine\godot.windows.opt.tools.64.exe"
   --headless --path . --script res://tests/run_all.gd`.
   Гонять **3 раза** — бывают флейки на случайных жителях. Новую логику
   покрывай проверками в `tests/run_all.gd` (блок на этап + регистрация в
   `_initialize`).
5. Живую сцену проверяй запуском:
   `godot --headless --path . res://scenes/city.tscn --quit-after 120`
   (и world/dungeon) — в выводе не должно быть SCRIPT ERROR.
6. Если менял версию: `data/version.json` → секция в актуальном
   `CHANGELOG_M14.md` (что/зачем/файлы/приёмка для заказчика) → отметить
   сделанное в `PLAN.md`.
7. Пересборка exe: команды из `build.bat` (импорт → тесты → экспорт
   `build/ПепелИМана.exe`; в bat есть `pause` — вручную удобнее по шагам).
8. Коммит: подробное описание по-русски (что, зачем, сколько тестов),
   затем `git push origin main`.

## Грабли (уже наступали — не повторяй)

- **Автозагрузки не работают** в режиме `--script` (тесты): `Game`/`Loc`
  недоступны, сцены не поднимают игру. Живые ошибки ловят запуском сцены
  (см. шаг 5), а не тестами.
- **Ошибка в скрипте роняет всё после**: `_ready` обрывается на упавшем
  `load()` (так пропадал HUD города), `_process` умирает посреди кадра (так
  ломался выход с карты). Одна опечатка = несколько «сломанных» систем.
- **`float % int` — ошибка компиляции GDScript** (урок v1.11.0, урок
  city_weather.gd). Список скриптов в тестах сканируется папкой целиком,
  не ведётся руками.
- **Флейки тестов**: случайные черты/болезни/заказы ломают сценарные
  проверки — в тесте глушить случайность (черты=[], sick_chance=0) или
  чистить списки перед шагом.
- **Староста не замещает строителя** (дизайн-решение) — работу закрывают
  поселенцы-строители или ручной труд героя.
- Куча ресурсов у здания ждёт носильщика — в общий пул не попадает сама.
- В GDScript нельзя объявить `var x` и `func x()` с одним именем.
